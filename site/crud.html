CRUD: Blade & API

make:crud writes a complete create, read, update and delete feature for one entity in a module: a JSON API, Blade pages, or both, on one shared backend.

The command

$ php artisan make:module Orders --api --web
$ php artisan make:crud Orders Order --api --web --fields="name:string,quantity:int,note:?string"
$ php artisan migrate
  • The first argument is an existing module, the second a singular entity name (Order, not Orders).
  • --api writes the JSON API, --web the Blade pages. With neither flag you get --api.
  • The module needs routes/api.php for --api and routes/web.php for --web. Create the module with the same flags.
  • For --web, the entity's singular and plural must differ: Sheep is refused, choose another name.

make:crud Orders Order --api --web

  • Generated Shared backend: model, migration, factory, StoreOrderRequest, UpdateOrderRequest, OrderData, CreateOrder, UpdateOrder, DeleteOrder, ListOrders, OrderPolicy.
  • Generated API side: OrderController, OrderResource, a route in routes/api.php, OrderApiTest.
  • Generated Web side: OrderPageController, five Blade views, a route in routes/web.php, OrderWebTest.
  • Refused before anything is written: a file already exists, the route file already has a route for the controller, a route name is taken, the entity is plural or reserved, a field is invalid, or a stub is out of date.

See also: make:crud options

Fields

--fields takes comma-separated name:type pairs. A leading ? on the type makes the field nullable. Names become camelCase properties and snake_case columns (dueAt is the column due_at). id, created_at and updated_at are added automatically and refused as fields.

Generated files

For make:crud Orders Order --api --web, paths relative to app/Modules/Orders/ unless shown in full:

SideFiles
SharedModels/Order.php, database/migrations/…_create_orders_table.php, database/factories/Orders/OrderFactory.php, Requests/StoreOrderRequest.php, Requests/UpdateOrderRequest.php, Data/OrderData.php, Actions/CreateOrder.php, Actions/UpdateOrder.php, Actions/DeleteOrder.php, Queries/ListOrders.php, Policies/OrderPolicy.php
--apiControllers/OrderController.php, Resources/OrderResource.php, a route added to routes/api.php, tests/Feature/Modules/Orders/OrderApiTest.php
--webControllers/OrderPageController.php, resources/views/orders/orders/{index,create,edit,show,_form}.blade.php, a route added to routes/web.php, tests/Feature/Modules/Orders/OrderWebTest.php
  • Views go to resources/views/<module-kebab>/<entity-plural-kebab>/.
  • Pages are plain Blade, with no JavaScript, and extend config('blueprint.layout'). The first --web run creates resources/views/layouts/blueprint.blade.php; later runs leave it alone.
  • With --web, the entity and field names are added to lang/<locale>.json for every configured language other than en. See Languages.
  • ListOrders returns the newest records first, 15 per page.
  • In a tenant module (tenant-saas) the migration goes to database/migrations/tenant/; run php artisan tenants:migrate instead of migrate.

Both controllers only take the request and return a response. The work happens in the shared Requests, OrderData, the actions and ListOrders. Create, update and delete run inside a database transaction.

Policy

OrderPolicy allows every signed-in user every action and denies guests. Guests get 403 on every route, also for ids that do not exist, so they cannot probe which records exist. Signed-in users get 404 for a missing id.

Tighten it. Each policy method has a // Tighten for your app. comment. For a token API, add auth middleware such as auth:sanctum to the API route group in the module's Provider.php. The Blade pages need a login of your own (Breeze, Jetstream or similar).

Feature gate

$ php artisan make:crud Orders Order --api --web --feature=orders

Adds ->middleware('feature:orders') to the generated routes, so they return 403 while the feature is off. It needs the saas or tenant-saas profile and a key defined in your Features class. It is refused for central modules, which have no tenant. See Features.

Tests

Each side gets a Pest test file. They cover:

  • guests are denied on every route, and cannot tell which ids exist;
  • list, create, show, update and delete as a signed-in user (the web tests also open the create and edit forms);
  • validation of the required fields (JSON errors for the API, session errors for the web);
  • with --feature: the routes are blocked when the feature is disabled;
  • in a tenant module: the routes are not served on the central domain. These tests run against a real test tenant.
$ php artisan test --filter="OrderApiTest|OrderWebTest"

Before running tests. If Pest is not installed, the test files are skipped with a message. Web tests fail with 419 when config is cached (php artisan optimize); run php artisan optimize:clear first.

Adding a side later

$ php artisan make:crud Orders Order --api
$ php artisan make:crud Orders Order --web

The second run writes only the web side. It reads the fields back from OrderData, so leave --fields out; a different --fields is refused. If the existing routes are gated by a feature, pass the same --feature.
