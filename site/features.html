Features & settings

In the saas and tenant-saas profiles, features switch capabilities on and off, and settings hold typed values. Both are defined in code. In saas there is one set for the app; in tenant-saas one set per tenant, stored in the tenant's database.

Feature definitions

engineering:install creates app/Shared/Features/Features.php (config blueprint.features). Every feature key and its default state live there and nowhere else:

final class Features
{
    public const ORDERS = 'orders';
    public const REPORTS = 'reports';

    public static function defaults(): array
    {
        return [
            self::ORDERS => true,
            self::REPORTS => false,
        ];
    }
}

State is stored in a features table (key, enabled). New tenants get the defaults from tenant:create. In saas, run php artisan features:sync once after migrating. A key with no row is off.

Checking and gating features

The Feature facade is read-only. An unknown key throws an error.

Feature::enabled(Features::REPORTS);
Feature::disabled(Features::REPORTS);
Feature::ensure(Features::REPORTS); // throws when disabled
Feature::all();                     // key => bool

Hiding a button is not security. Check on the backend:

WhereHow
RoutesMiddleware feature:orders, or feature:orders,reports (every listed feature must be on). 403 when off.
Generated CRUDmake:crud Orders Order --feature=orders adds the route middleware and a test for it. See CRUD.
Jobsnew RequireFeature(Features::ORDERS) in the job's middleware() (Best\Blueprint\Features\RequireFeature)
Actions, controllers, scheduled tasksFeature::ensure(...)
Navigation, widgetsBlade @feature('orders') … @endfeature. Display only.

In tenant-saas, when no tenant is active every feature reads as off.

Feature commands

Feature state changes only through the console, by platform admins.

$ php artisan feature:list --tenant=acme
$ php artisan feature:enable reports --tenant=acme
$ php artisan feature:disable reports --tenant=acme
$ php artisan features:sync

feature:enable reports --tenant=acme

  • Note Writes the reports row in tenant acme's features table as enabled, inside that tenant's database.
  • Refused without --tenant in tenant-saas, with --tenant in saas, for an unknown tenant, or for a key not in Features.

See also: feature:enable · feature:disable · feature:list · features:sync

features:sync adds keys that are defined but have no row yet, with their default state. It never changes existing rows. In tenant-saas it runs for every tenant, or only for the ones you pass: --tenant=acme --tenant=beta. All listed tenants are checked before any is changed.

Setting definitions

engineering:install creates app/Shared/Settings/Settings.php (config blueprint.settings):

self::APP_NAME => ['type' => 'string', 'default' => 'My App', 'editable_by' => 'tenant', 'ability' => 'manage-settings'],
self::APP_LANGUAGE => ['type' => 'string', 'default' => config('app.locale', 'en'), 'editable_by' => 'tenant', 'ability' => 'manage-settings'],
self::ORDERS_AUTO_CONFIRM => ['type' => 'bool', 'default' => false, 'editable_by' => 'platform'],
KeyMeaning
typestring, int, float, bool or array
defaultReturned when nothing is stored
editable_bytenant (changed from app code) or platform (console only)
abilityGate ability a user needs to change a tenant setting; required for those

A row in the settings table exists only after a value was set. New tenants need no setting rows.

Reading and writing settings

Setting::get('app.language');        // typed value, or the default
Setting::set('app.language', 'ar');  // tenant settings only, through their Gate ability

Setting::set() refuses platform settings, values of the wrong type, and users the Gate denies. Define the ability the generated settings use, for example in AppServiceProvider::boot():

// Example only: decide who may change tenant settings in your app.
Gate::define('manage-settings', fn (User $user) => $user->is_owner);

Setting commands

$ php artisan setting:list --tenant=acme
$ php artisan setting:set orders.auto_confirm true --tenant=acme

setting:set orders.auto_confirm true --tenant=acme

Platform admins can set any setting, tenant or platform. The value is read as JSON (true, 5, ["a"], "text"); anything that is not valid JSON is taken as plain text. Put -- before negative numbers.

  • Refused an unknown key, a value of the wrong type, a missing --tenant in tenant-saas, or --tenant in saas.

See also: setting:set · setting:list

Who can write

WriteAllowed from
Feature stateConsole commands only (platform admins)
platform settingsConsole commands only
tenant settingsApp code via Setting::set() with the Gate ability, or the console

The admin writers behind the commands refuse to run while an HTTP request is being handled, including in your app's own HTTP tests, and in tenant-saas when no tenant is active. In saas tests the features table starts empty, so every feature is off; call app(\Best\Blueprint\Features\FeatureAdmin::class)->sync() or ->enable('orders') in beforeEach.
