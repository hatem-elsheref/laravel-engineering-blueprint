Profiles

A profile decides what the package sets up in your app. There are four, each one adding to the one before: basic, modular, saas and tenant-saas.

Compare

modularYes, in app/Modules/NoNo

  • basic: a standard Laravel app that follows the package conventions. The module generators (make:module, make:dto, make:action, make:crud) refuse to run.
  • modular: business code lives in modules under app/Modules/. This is the default profile.
  • saas: modular plus features and settings stored in the app database.
  • tenant-saas: saas plus multi-tenancy. Features and settings live in each tenant's database.

Install a profile

$ composer require best/laravel-engineering-blueprint
$ php artisan engineering:install --profile=saas

Without --profile the command asks, offering the profile already recorded or blueprint.default_profile (modular). In a non-interactive shell it uses that default.

engineering:install --profile=saas

Checks PHP and Laravel versions first, then records the profile and sets up what the profile needs. Safe to re-run: finished steps print already set up.

  • Generated config/blueprint.php with 'profile' => 'saas' (created, or the profile line updated).
  • Generated app/Shared/Features/Features.php, app/Shared/Settings/Settings.php and the features and settings migrations (saas and tenant-saas only).
  • Refused an unknown profile, an incompatible environment, or a move to fewer capabilities without --allow-downgrade.

See also: engineering:install options · engineering:about

What install writes

ProfileFiles and changes
Every profileconfig/blueprint.php with the profile recorded. A cached config is cleared.
saas, tenant-saasFeature and setting definition classes in app/Shared/; migrations for the features and settings tables (in database/migrations/ for saas, database/migrations/tenant/ for tenant-saas).
tenant-saasRuns tenancy:install (once), an empty tenant route group in routes/tenant.php, app/Models/Tenant.php, tenant_model and central_domains in config/tenancy.php, a copy of the users migration in database/migrations/tenant/, and registers App\Providers\TenancyServiceProvider. See Tenancy.

The command ends with the next step for the profile, for example php artisan migrate && php artisan features:sync for saas. Check the recorded profile and environment at any time:

$ php artisan engineering:about

How to choose

If your appUse
Is small, or you only want the conventionsbasic
Has several business areas (orders, products, inventory)modular
Needs capabilities switched on and off, or typed settings, for one customer basesaas
Serves many customers, each with its own subdomain and databasetenant-saas

When unsure, start with modular. Moving up later keeps your modules and generated code.

Moving up

Run the install command again with the bigger profile. Existing modules and generated code are kept.

$ php artisan engineering:install --profile=saas
$ php artisan migrate
$ php artisan features:sync

For tenant-saas, install stancl/tenancy first:

$ composer require stancl/tenancy:^3.10
$ php artisan engineering:install --profile=tenant-saas
$ php artisan migrate
$ php artisan tenant:create acme

Modules made before tenant-saas. Their routes use neither the tenant nor the central middleware group. The install command lists them, and make:crud refuses them until you add 'tenant' (data per tenant) or 'central' (platform) to the Route::middleware(...) calls in their Provider.php.

Moving down

A profile with fewer capabilities (for example saas to modular) drops features, settings or tenancy. In an interactive shell the command asks you to confirm; otherwise it refuses unless you pass --allow-downgrade:

$ php artisan engineering:install --profile=modular --allow-downgrade

It warns about modules the change breaks: modules using the tenant or central route groups, and modules whose routes use feature: middleware. It does not delete files.

--force rewrites config/blueprint.php from the package copy and saves the old file as config/blueprint.php.bak. It also skips the downgrade check.
